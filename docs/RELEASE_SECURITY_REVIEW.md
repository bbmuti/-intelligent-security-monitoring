# Public Release Security Review

Review date: 2026-08-24

This document records the repository checks completed before the first public release. It is evidence for the release checklist, not a claim that the software is production-ready.

## Repository history

The complete local Git history was scanned, including every reachable commit and tracked path.

- A pattern-based history scan checked for GitHub, AWS, OpenAI, generic bearer-token, private-key, and high-risk credential formats.
- `detect-secrets` 1.5.0 independently scanned the working tree and history candidates.
- Sensitive-looking assignments were manually reviewed in CI, E2E, test, and example configuration.
- The only environment file ever tracked is `.env.example`; no `.env` file, database, downloaded dataset, production log, or private configuration was found.

Result: no real secret, private URL, personal data, or production telemetry was identified.

## Reviewed false positives

The scanners correctly highlighted values that resemble credentials but are deliberately non-secret:

- `ci-*` and `e2e-*` values used only by isolated GitHub Actions jobs;
- `change-me` and `replace-with` placeholders in examples;
- synthetic test credentials created inside test fixtures;
- SHA-256 dataset integrity hashes and deterministic cache identifiers.

None of these values grant access to an external account or deployed service. Demo credentials must remain local and must never be reused for another system.

## Telemetry and screenshots

The committed examples and automated demo flow use synthetic identities and the documentation-only IP ranges defined by RFC 5737. Portfolio screenshots are generated by the Playwright analyst-flow test after it creates synthetic application events; the workflow fails when the screenshots cannot be produced.

## Automated controls

The CI workflow performs a full-history Gitleaks scan, dependency audits, static analysis, backend and frontend tests, browser E2E validation, database migration checks, Windows collector syntax validation, and container builds. The workflow uses read-only repository contents permission and pins third-party actions by commit SHA.

## Release boundary

Immediately before changing repository visibility:

1. confirm that the latest `main` CI run is green;
2. confirm that the screenshot artifact matches the committed images;
3. enable GitHub private vulnerability reporting;
4. verify repository topics and the security reporting link;
5. obtain explicit approval for the visibility change.
